01 · 这场实验

三天，一家公司，直播进行

Grok Bot 团队的三个人——Matt Palmer、Roshan 和 Lauren（「Potato」）——坐进旧金山一间演播室，面对一个空的 GitHub 组织、空的 Slack、空的 Notion，以及没有想法。七十二小时后，他们有了一款几千用户的上线产品。这份指南里的一切都来自那三场直播。

第 1 天 — 构思

餐厅快闪变成快闪平台，变成艺术展，变成周边快闪。一天四个转向。软件从来不是瓶颈；对齐该做什么才是。

第 2 天 — 构建

转向游戏工作室。一个一次性 HTML 自走棋原型，代号 Cupcake，现场做出并玩起来——属性 bug、作弊演示全有。

第 3 天 — 上线

夜里机器人工厂落地 170 个 PR。游戏在上午 10 点以 Thursday Arena 上线。收工时：433 个 PR，约 30,000 次浏览，约 6,000 局，收入 $0。

◎ 为什么一份直播指南值得读

产品文档描述功能做什么。三天未经剪辑的现场构建，让你看见人们在时间压力下实际拿它做什么——哪些模式站得住，哪些太贵，哪些悄悄坏掉。这里几乎每一条都是有人被看见在做的实践，不是有人描述过的功能。

关于名字：自动字幕把产品打成「GrokBot」「Rockbot」「Brockbot」，把公司打成「SpaceX AI」。都是同一件事。数字是现场说的，当天就是移动靶。

02 · 心智模型

队友，不是任务

产品创作者之一 Roman 在第一场直播开场抛出整件事赖以成立的论点：「我们真的希望 Grok Bot 感觉像在和队友、同事一起工作。」界面刻意做成 iMessage 的形状，而这个形状驱动了本指南里每一条好做法。

产品押上的三个赌注
  1. 1队友范式，不是任务范式。机器人是你会回去找几个月的具名同事，不是开完就丢的线程。它会积累。
  2. 2每个机器人有自己的电脑。一台带浏览器的 Linux VM。它能用遗留软件、政府门户、没有 API 的站点——人拿屏幕和鼠标能做的，它都能做。
  3. 3一切在云端跑。合上笔记本，工作继续。「你度假时它能干活。你睡觉时它能干活。」

实践上会变什么

  • 你是在雇人，不是在填配置。给机器人划范围，更像写职位描述，而不是填设置页。
  • 纠偏会复利。告诉机器人它为什么错，是投资，不是打断。
  • 你回来面对做完的活。Amrita 的原话：「做完的活才是 Grok Bot 最好的部分。」
  • 打断没问题。任务中途改道是正常的，而且被鼓励。

模型 vs. 套件

Roshan 把这条线画得很清楚，决定工作该发生在哪时很要紧：

  • Grok 是模型。
  • Grok Bot 是套件——刻意轻量，擅长编排、用工具和判断。
  • Cursor 云端智能体 是重型编码套件，真正的工程活由机器人委派给它。

在 Grok Bot 里做原型。通过云端智能体发货。

「走到 90% 和端到端、放手做完，体感真的完全不同。真的很神奇。」

03 · 架构

一个机器人实际拿到什么

搞清机器人之间共享什么、不共享什么，就能解释直播里大多数让人吃惊的行为——好的和坏的。

自己的电脑

每个机器人一台 Linux VM，带浏览器、终端和可安装应用。一个机器人碰不到另一个的屏幕——这份隔离让两个机器人能同时改同一套幻灯片的不同页。登录、2FA、CAPTCHA，或不想交出的事，你可以自己接管屏幕。因为 VM 是 Linux，不兼容 Linux 又没有 MCP 的工具完全不能用。问答里说得很直白。

自己的记忆

记忆按机器人隔离、长期保存、可编辑。你说一次的偏好会留下来。每个机器人还有自己的上下文上限——这就是按角色拆活的实际原因。你可以让它忘掉某件事，同时也会少耗 token。复制机器人会复制人设，记忆从零开始。

共享文件系统

机器人共享文件，不共享上下文——「一台 VM，一堆不同实例，就像你有不同桌面。」技能是全局的。教给一个，所有机器人都能用。浏览器登录存在机器上，任务之间还在。

两种碰到工具的方式

连接器 / MCP——「给智能体的 API。」更快、更便宜、更容易加白名单。有就用。Computer use——没有 API 时的通用退路。更慢、更贵。把 MCP URL 丢给机器人，它会自己装连接器。

三天里出现的平台：macOS、Windows、Linux、iOS、iPadOS、Android。设置里还有本地执行开关，让机器人在你自己的机器上行动，而不是云端 VM——团队自己强烈偏向云端，为了并行，也因为本地应用会抢焦点。

⚠ 共享文件系统不是安全边界

文件和浏览器会话是共享的，记忆不是，所以分开的机器人给你的是注意力隔离，不是访问隔离。若要真正的边界，用登出、连接器范围和账户权限来划——不是再做一个机器人。

04 · 搭建角色名册

一个机器人，一件事

这是三天里被重复最多的建议，每位讲者各自独立说到。不是一个通用助手——而是一份窄域专员角色名册，你按名字点他们。

它更好的四个原因
  1. 1上下文保持收束。每个机器人有自己的上下文上限。一个通才同时抛四个不相干的活，会烧光它然后开始忘事。
  2. 2你能记住该问谁。Ling Shi 的框定：「我们的脑子也存不下长篇小说——你得知道该点谁的名。」
  3. 3被派入角色后，模型表现更好。职责窄到反馈有意义，学习环才会收紧。
  4. 4并行几乎免费。一次派出五个专员，让他们干活，回来再综合——人开会 → 分组 → 再对齐的那套。

好角色会写明

  • 一块清楚、窄到能起名的职责
  • 可以使用的具体工具和数据源
  • 它如何开展工作，而不只是工作是什么
  • 发生前需要你批准的事项
  • 若这份工作有周期，写明日程

避开「万能助手」。往窄里写：人才侦察、费用管理、Bug 复现。

整理侧边栏

  • 分区像组织架构：领导层、工程、作战室。
  • 标签只是提醒专长，食物名机器人一多就有用。
  • Simon 按职能配色：调研橙色、客户绿色、外拓另一种——一眼线程就知道流水线阶段。
  • 钉住你每天真正用的三四个。

起名不是装饰。团队从聊天里众包名字——Tater、Whisk、Bake、Crumble、Dr. Eggbot——而且确实改变了他们谈论工作的方式。有名字的机器人会被委派；「任务 3」会被微观管理。

⚠ 机器人膨胀陷阱

名册最大的 Simon 说得很冲：「我保证有些时候我搞过太多。老实说更乱。你真该问：这件事为什么非得由一个新机器人来做？」Blake 从另一头给了同样的建议：「团队保持精简，你不需要 45 个机器人。」拉起机器人的本能又便宜又好玩，所以才需要一条规则。优先给现有专员加技能或例行任务，而不是新雇一个。

05 · 元机器人

会建机器人的机器人

三天里用得最多的机器人不是工程师，也不是研究员。是 Dr. Eggbot——整份工作就是创建、审查和改进其他机器人。直播上几乎每一个新队友，都诞生于打给它的一句话。

元机器人做什么

  • 从一段白话职位描述创建机器人
  • 写它们的描述——这个字段就是系统提示词
  • 审计名册：「评审我们所有机器人——瓶颈在哪？」
  • 给它们起名，好到两个人分开提示，都得到一个叫「Ping」的机器人

描述字段就是灵魂

Description 不是标签。Lauren：「有人叫它灵魂，或系统提示词。」它会实质改变声音、判断，以及机器人如何委派。

  • 写成原则，不要写成事件
  • 写明它负责什么、必须交出什么
  • 明确点名它的事实来源
过拟合失败——以及修法
DR. EGGBOT 第一次写的描述
「关于我们游戏工作室的高层背景。一件事：通过 pstack potato mode 和云端智能体编排工作，再监督并验证，从而对工程结果负责。匹配你的手册并遵守它。」

Lauren 的判决：太具体。它把今天的工具链和今天的事故写进永久身份。

纠偏
「再读一遍 potato mode，提炼出 Cupcake Eng 应遵循的原则，而不是这些过于具体的问题。」

这是你写每一项技能和规则时的一般规则，不只是机器人描述。

有合适的就从市场模板起步。模板会带上记忆、例行任务和集成，分享时剥掉凭证和聊天记录——团队自己的建议是：有模板就不要从零开始。

◎ 你开口问，机器人会自己组班子

第 2 天 Amrita 问两个现有机器人：「基于你正在做的工作，哪些机器人能帮你继续把活做好？直接帮我把那些机器人拉起来。」它们产出了三个新专员——Battle Card Blair、Demo Drake 和 AI Radar——各自有书面角色和声明的事实来源。问名册缺什么，是一步真能用的棋。

06 · 自动化

技能与例行任务

两块积木。技能抓住怎么做。例行任务决定何时发生。直播里几乎每一条能沉淀的工作流，都按这个顺序建，而且至少亲手做过一遍之前不上。

先亲手做一遍→ 得到可靠结果→ 存成技能→ 配上例行任务

技能的三种做法

  • 靠演示。点「teach a task」，把自己做一遍录下来，机器人把录像变成可复用技能。现场用来教幻灯片动画和竞品博客扫描。
  • 靠纠偏。价值最高的来源——见下。
  • 靠写下来。过程里有决策逻辑、错误处理或批准闸门时，一次演示不够让机器人推断出来。亲手补上。

技能是全局的：教给一个，所有人都能用。

例行任务需要定义什么

  • 哪个机器人拥有它
  • 日程和时区——或事件 / webhook 触发
  • 输入从哪来
  • 期望的输出格式
  • 批准边界
  • 失败时怎么办
  • 无事可报时怎么办——告诉它空操作时保持安静

◎ 沉淀纠偏，不要沉淀事故

Roshan 的规则：「只要看见智能体想错了，多半就是做一条技能来修好它的好时机」——而不是绕开再提示一遍。Ling Shi 的版本更利：再往下沉一层，而不是去修下水道。但另一边有陷阱。规则是针对一次糟糕会话写的时，「智能体往往会把那次会话的全部细节塞进规则——然后技能就不太能用了，因为过拟合。」写原则。删掉事故。

例行任务频率是钱悄悄消失的地方——见第 12 节。优先事件触发而不是定时；优先一天一两次，而不是每十五分钟一次。

07 · 软件工厂

433 个 PR 是怎么合进去的

「软件工厂」是产出那个头条数字的模式。团队不喜欢这个词——「我其实不太喜欢工厂这个说法」——但还是留下了。剥掉品牌，它就是一个闭环：实现者写一小段改动，验证者跑应用并试图弄坏它，只有这时才合并。

这个闭环
  1. 1计划被拆成阶段。Lauren 的 Pstack 插件和它的「Potato Mode」技能做这件事：/potato mode 加上「完全自动驾驶这个计划。」
  2. 2实现者智能体写小 PR。Cursor 云端智能体，每个有范围的改动一个，各自一台机器。
  3. 3验证者智能体跑应用并模糊测试。「swarm」技能派出一队智能体，真的点进正在运行的产品找损坏。
  4. 4绿灯自动合并。验证通过才是合并门禁——不是人读 diff。
  5. 5试玩机器人把整件事端到端玩一遍。「Chrome」盯着 CI 绿灯的 PR，在放行前玩真游戏。

自动驾驶阶梯

  • 只排查——「先别开 PR，先回来告诉我你觉得发生了什么」
  • 草稿——开 PR，等人
  • 自动驾驶——实现并验证，绿灯即合并
  • 完全自动驾驶——规划、分阶段、实现、验证、合并

一旦上线，Lauren 有意降了一级：「也许别完全自动驾驶——我们敢吗？」

Architect 这一步

Pstack 的「architect」技能把同一个问题并行扔给四个不同模型，再由一轮评判合并或挑出获胜计划。

值得为架构决策用，因为不同模型会浮出不同约束。一次性原型明确跳过了——「这个点上我其实不在乎架构。」

⚠ 诚实的限制

Lauren 谈这款游戏：「老实说，我完全没看过代码。我就用了 potato mode 和 Pstack。」做真正 Grok Bot 产品的 Eric 同样清楚：他在真实代码库上不会这样干——他读每一个 PR，并亲手执行反模式规则。工厂的激进程度应按影响范围缩放，而 72 小时的演示游戏大概是影响范围能有多低的下限。

08 · 验证

验证才是整场游戏

若要从这三天里只带走一条构建指令，就带这一条。每个用机器人正经发过东西的讲者都说过一个版本；还没建的人则说这是他们的瓶颈。

「验证太重要了。你需要机器人真的去跑代码、截图。这会让你对它真的理解问题有大得多的信心。」

Lauren · 第 3 天
验证技能实际包含什么

智能体能驱动的 CLI

不是每次临时新写的脚本——那些浪费 token，也不可复现。Lauren：「你需要的是 CLI、脚本或某种工具，让机器人能可靠、确定地与应用交互。我更希望它就有一套标准工具。」

功能地图

应用功能与流程的机器可读地图，让智能体不用猜就能导航到要测的东西。Thursday Arena 走得更远，做了 /rules 页和 llms.txt 风格端点，让智能体能读游戏自己的规则。

团队执行的三条规则
  1. 1先复现再修复。「只有它们真能复现这个 bug，我们才能相信智能体理解了问题。」常驻提示词：「写任何代码之前，先跑应用，找到确切的 bug 和表现，然后再动手。」
  2. 2证据放进 PR。手册里的书面规则：UI 用截图或录像，后端用性能指标。云端智能体能录自己运行的视频并附上。
  3. 3给技能起名，并按名字调用。他们的是 /verify cupcake，游戏上线后，每一条自动驾驶指令都把它写成不可商量。

◎ 可推广的检验

Eric 选择自动化什么的启发式：「看你的工作流，问什么循环是可验证的——那就是让机器人放开干的地方。」编码是典型情况，因为测试、构建和正在运行的应用给出机器可读信号。没有这种信号的事，必须先发明信号，自主才安全。

没有验证技能，失败模式具体且眼熟：机器人做完，说「好了，现在你跑应用、点一圈，告诉我行不行。」时间就花在那一来一回上。

09 · 提示词模式

真正赚回成本的七个动作

这些不是巧妙的提示词把戏。它们是三天里六七个不同讲者各自独立表现出来的那一把习惯。

先复述一遍
几乎人人都用
长或复杂的指令后面，加上「用你自己的话复述一遍」再让它开始。在误解还免费的时候抓住它。第 2 天被称为「我最喜欢的模式。」
先碎碎念，再结构化
语音口述
对着麦克风意识流说一两分钟，再让机器人综合。想法在说出口时就被接住，不用稍后重打——团队曾在对话中间这样记下增长点子，还是直播。
先蒸馏，再推理
用于很长的输入
很长的口述提示词上，先让机器人蒸馏成关键事实，再基于蒸馏结果推理。Blake 对付东拉西扯输入上幻觉的办法。
先说产出
Amrita

从直播里抽出，尽量少整理。形状才是课：产出、约束、事实来源，以及做完时做什么。

「设一条例行任务，每五分钟检查云端智能体。看它们是否跑偏——比如在跑很长的 sleep，像 sleep 300——或偏离我们的目标，过于保守。在你发现它们跑偏的当时，打断并推一把。」
Ling Shi。他的点：反复对智能体说「这个很急」，会让它跳步骤、瞎猜。定义好的策略不会。

管一支团队，不是一个工具

大约过了五个机器人，每条消息都自己路由就成了瓶颈。越过那一点，四种模式反复出现。

1 · 幕僚长

  • 你几乎只跟这一个机器人说话；它分发给专员并汇报回来
  • 它自己接入新机器人——把上下文和手册发给它们，这样你不用重复
  • Simon 的规则：其他每个机器人都通过它来建，这样它知道各自是干什么的
  • Blake 在一名幕僚长下管 15–20 个专员，没有中间经理
  • 不是人人适用——Shub 更喜欢直接跟专家说话，而且会明说

2 · 手册广播

  • 一个机器人拥有团队标准的活手册，通常在 Notion
  • 新标准只告诉它一次，由它传播
  • 「你只需要把该做什么想一遍……所有工程师都会知道，不用你挨个通知」
  • 标准示例：每份 PR，UI 带截图，后端带性能数字

3 · 幕僚会议

  • 把几个机器人拉进同一线程，从不同视角争论一项决策
  • Blake 要求他们永远要不同意——「光附和没有用」
  • 幕僚长综合并回报建议
  • 警告：群聊急切、爱说话、而且贵。用于决策，不用于例行工作

4 · 子机器人军团

  • 中层机器人把大批量工作委派给一群低上下文工人
  • Simon 的「士兵」通过共享群聊并行调研 100–200 个客户
  • 容易放大缩小；产出回流到一个父级做审计
  • 和工程集群同一形状——一个编排者，许多一次性工人

◎ 还没人解决的诚实问题

有人问管这么多并行智能体是什么感觉，Matthew Berman：「我完成的工作比以往都多。我也比以往都忙。」在十几个正在运行的智能体之间切换上下文，是真实且目前未解决的成本。幕僚长模式是现有最好的答案，而它是缓解，不是根治。

实际花多少钱

计费按用量：你为跟机器人说话和机器人自己的 computer use 付费。这些是直播里报过的真实数字，旁边是人们被看见浪费钱的四个地方。

$20–30

$1–2
端到端解决一张中等复杂度支持工单
$0.20
低复杂度工单分桶并批处理后，每张工单
~$1,000
一个机器人找到更便宜的公用事业套餐，一年省下的；人只花了 60 秒注意力
四处漏洞
  1. 1过于频繁的例行任务。遥遥领先的最大驱动。「如果你有三条每 15 分钟跑一次，那就是一天几百条消息。」审计频率；优先事件触发；一天一两次通常就够。
  2. 2已有 API 却走浏览器自动化。靠 computer use 填网页表单，比原生 API 路径更贵。Shub 的招：看机器人用浏览器做一次，让它检查触发的网络请求，然后从此直接打那些端点。
  3. 3一直开着的群聊。群聊里的机器人互相抢话，很快就变贵。例行工作优先一对一打标签。
  4. 4机器人膨胀。每多一个机器人，就是更多例行任务、更多要重建的上下文、更多重叠。精简名册就是更便宜的名册。

你能扳的杠杆

  • 调整机器人的详略——说话风格直接改变 token 花费
  • 告诉机器人忘掉不再需要的上下文
  • 向 Grok Bot 自己要针对你这套配置的优化建议
  • 留一个唯一工作是优化其他机器人的例行任务和技能的机器人

不是杠杆

Computer use 的算力本身用户调不了。少花的办法是少用：有 MCP 就接 MCP，只有别的路走不通时才伸向浏览器。

带刹车的自主

Matthew 的表述是任何人给过的最干净的一句：「信任你的机器人，给它们能动性——同时给护栏，知道事情不会偏太远，因为发出任何东西之前它们总会回到你这里。」

Auto Review 和规则

  • 内置分类器判断动作有多险，并据此询问
  • 你再叠明确规则：「未经先问我，永远不要回邮件」「你可以不经询问就做幻灯片」
  • 按动作类型的开关——例如部署到生产始终先问
  • 它偏谨慎：一个机器人在建表单前先检查表单是否在收集 PII

凭证

  • 密钥经安全表单进保险库——智能体看不到原始密码
  • 活动中途上了 1Password 集成；机器人可以从保险库重新鉴权
  • 分享的模板带走记忆、设置、技能和例行任务——不带走凭证或聊天记录
  • 完全不想委派的登录，自己接管屏幕
直播里用硬方式学到的三课
  1. 1任何竞争性的东西必须以服务端为准。游戏逻辑跑在客户端时，Matt 打开开发者工具，直播改自己的属性。给调试 UI 加功能开关帮不上——决心足够的用户仍能打开。这条代码路径必须不存在于客户端。
  2. 2用户提交的文本是攻击面。他们的反馈管道带着客户端长度检查、服务端脏话过滤、输入消毒、基于模型的内容护栏、限流——以及给分诊机器人的明确指令：提防提示词注入。
  3. 3一次自主修复可以把生产打挂。确实发生了：工厂一条糟糕的 SQL 在直播中把线上游戏打挂，而他们正说到克制。几分钟内可恢复——但这就是迁移和部署必须留人闸的论据。

◎ 新机器人的爬→走→跑阶梯

David 给客户支持的进阶几乎可推广到任何事：先是一个只读和摘要的机器人；然后一个把回复写成内部备注的；只有被信任之后，才发送和行动——影响范围最大的动作仍需批准，比如编辑面向客户的知识库。「从简单开始。让机器人迁就你怎么工作，而不是反过来。」

直播里坏掉的

未经剪辑的直播格外诚实。这些失败发生在观众眼前，以及每一条产生的规则。

智能体让规则过拟合

第 2 天

一次事故之后写的机器人描述，把那次事故永久写死。规则：技能或规则诞生于一次糟糕会话时，剥掉会话，留下原则。

闪光效果吞掉了每张卡

第 2 天

标识稀有度的 CSS 闪光被用得太猛，所有卡看起来一样。智能体优化了效果，不是目的。规则：说清用来区分的结果，不要说视觉。

真实落地页上的虚构内容

第 2 天

智能体发明了看起来像那么回事的示例机器人，而不是用真实市场，并把内部原型用语漏进面向用户的文案。规则：点明事实来源，并说「真的去查。」

所谓 3D 原型并不是 3D

第 2 天

要求 3D 动画，智能体做出了 2.5D——从没人告诉它用 3D 库。规则：任何有广为人知的库的事，点出库名。

用开发者工具作弊

第 2 天

客户端游戏逻辑意味着属性可以从浏览器控制台改，还是直播。规则：任何竞争性的东西都以服务端为准；功能开关不是安全措施。

机器人无视团队政策

第 1 天

在有意直推 main 的阶段，一个机器人开了 PR。规则：没写下来的规范就不是规范。写到机器人会读的地方。

VM 上的会话掉了

第 2 天

Karen Cheng 的自动化坏了，因为机器人的浏览器不断从她本地已登录的服务登出。规则：必须无人值守跑的，优先用连接器而不是浏览器会话。

工厂把生产打挂了

第 3 天

一次自主修复的糟糕 SQL 弄坏了线上游戏。规则：迁移和部署留人闸，无论闭环有多好。

屏幕上出现了活的 API token

第 3 天

几秒内抓住并吊销，但它发生了。规则：密钥处理里的薄弱环节是人，不是保险库。

垃圾信息涌进反馈管道

第 3 天

上线几小时内。20 字符下限、脏话过滤、消毒、基于模型的护栏和限流都是事后补的。规则：审核和表单一起发，不要事后补。

18 · 限制与路线图

它现在仍会说不的地方

直播里说得很直白，通常在问答。在你围绕还不存在的东西设计工作流之前，值得知道。

今天的硬限制

  • 仅 Linux。既不兼容 Linux、又没有作为 MCP 暴露的工具，完全不能用。问答里干脆的「不行」。
  • CAPTCHA 会挡住机器人。没有通用绕过；建议是封掉机器人不该去的站点，而不是躲避检测。
  • 没有跨账号机器人消息。你的机器人不能跟别人的说话。「非常酷的用例，我们为那个兴奋」——但还不存在。
  • VM 上会话会掉。浏览器登录独立于你本地的过期，弄坏无人值守自动化。
  • 没有从其他智能体栈迁过来的路径，除了导入模板、让它指向已有上下文。

当时说正在到来

  • 双向语音模式——第 3 天直播宣布，随后几天推出。演示过打电话给机器人检查并合并 PR。
  • 多人——人和机器人在共享聊天里。当时只能在 Slack 里 @ 一个机器人。直播里反复被要求。
  • 多机管理——机器人管几台机器会搞混；正在积极改进。
  • 按角色入职——新用户被问工作，并拿到匹配的起步模板。
  • Computer use 速度——「非常热的话题」，预期随后几周改进。

数字和功能以直播当时所述为准，之后会变。把限制这一节当形状，不当规格：任何承重的东西，构建前先对照当前文档。

◎ 没人有答案的那一个

确定性。模型不是确定性的，机器人一旦在执行政策，这就成问题。给出的办法是结构性的，不是魔法：让机器人写代码——决策树或函数——然后每次政策决策到来时调用那段代码，而不是每次重新推理。和验证 CLI 同一直觉：答案应该两次一样的地方，用工具替换判断。

他们在结尾承认了什么

第 3 天最后半小时是七十二小时直播里最有用的部分，因为团队停止演示，开始评估。

「做任何东西最难的部分——即便有无限的 AI 能力——是让人在乎。」

Roshan · 收工复盘
五条结论
  1. 1分发是它能成的唯一原因。采用来自直播，不是产品本身有多打动人。第 14 节每一个数字都带着这个星号。
  2. 2围绕你已经会的事做生意。天真版本——「我只要提示词模型去赚钱」——失败了。一个专职营收智能体跑了一整天，产出正好 $0。
  3. 3对齐想法比把它做出来更难。第 1 天产出四个转向和零产品。软件从来不是拖慢他们的东西。
  4. 4克制现在是一项必需技能。Lauren：「你几乎能做出任何你想要的——百万功能却不好用的产品。你现在必须有纪律。」砍机制才让他们发出去。
  5. 5发现仍是人的。「你必须作为人走出去，有机地发现所有问题。一旦你搞清怎么解决它们，就可以做成机器人，让它们永远跑下去。」

机器人真正擅长的

  • 补知识缺口——团队在他们谁都不懂的领域发了货
  • 没人想做的重复验证
  • 跨三天项目握住没人能装进脑子的上下文
  • 把一句说出口的想法变成已记录、已排序的条目，而不打断对话

仍留在人这边的

  • 决定什么值得做
  • 对功能说不
  • 注意到游戏还不好玩
  • 关系、信任，以及含糊的判断

Roshan 的自检，值得偷走：定期问「我是不是太深地卡在循环里？我怎么能让这更自主？」——并让一个机器人按例行任务来问你。

你的第一周

顺序安排成每一步都让下一步更便宜。Lauren 自己对什么最重要的排序不是你会以为的：「Grok Bot 最重要的甚至不是搭你的机器人。是接上你所有不同的工具和插件。」

  1. 1先接你每天已经在用的栈。在做任何一个机器人之前。Slack、邮件、日历、你的事项追踪、你的仓库。连接器在速度、成本和可靠性上每次都赢过浏览器自动化。
  2. 2录 15 分钟语音备忘。你是谁、工作是什么、什么是坏的、什么该自动化。把转录交给第一个机器人，让它提案一套系统。
  3. 3挑你一天里最烦的那部分。Amrita 给第一批任务的建议，也是 Karen Cheng 找项目的办法。不是最能拿得出手的——是最烦的。
  4. 4创建一个窄域专员，先只读。读和摘要。然后写成内部备注。然后，一旦你信任它，再行动。在你需要之前设好批准规则。
  5. 5在机器人看着的情况下，亲手把活做一遍。用「teach a task」。然后亲手补上决策逻辑、错误处理和批准闸门——一次演示推断不出来。
  6. 6在第二个机器人之前先建验证闭环。哪怕再粗糙。如果机器人能对着真东西检查自己的活，这之后的一切都更快更便宜。
  7. 7到现在，才加幕僚长。并且之后每一个机器人都通过它来建，这样它知道各自是干什么的。
  8. 8把纠偏沉淀成原则。每次它想错了，写下一般规则——不是那次事故。这就是让第三个月和第一周不一样的复利。
  9. 9周五审计你的例行任务。钱花在频率上。任何能改成事件触发的定时，都改掉。

◎ 以及不要做的那件事

不要因为好玩就拉起一个机器人。它确实好玩，问题就在这里。每个新雇都要耗费上下文、例行任务和注意力，而这些直播里管最大名册的人，对保持精简喊得最响。当你觉得手痒，先问现有专员是不是只需要一项新技能。

「为什么不是今天？」

Roshan 永久的 Slack 状态，也是这份指南能拿到的最好收束
